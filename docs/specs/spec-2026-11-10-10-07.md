# StarBridge：目标与当前改进问题

记录日期：2026-11-10。当前可用代码基线：`f7eef6851aff47d6090f7764e6fb2974099a2617`。

本文按用户要求保存已确认目标与当前差距，不新增需求、不固定后续技术方案，也不表示恢复自动开发。完整需求以[StarBridge需求文档](<../../StarBridge.md>)为准；持续更新的任务状态以[当前工作](<../../TODO.md>)为准。本文的实现状态是上述交付基线的快照。

**当前结论：AI通过Java API实际操作STAR-CCM+的通用工作链已经可用，但低成本查资料、复用代码并顺畅完成复杂任务的能力，仍未达到目标。**

## 一、我们的目标

### 1. 让AI实际接管算例工作，而不是只生成代码

AI应能结合用户经验、实际版本资料和当前算例信息，编写、修改、复用并执行Java宏，完成已有算例的参数工作、真实问题排查，以及从零建模到获取结果的连续操作。必要的执行工作不应重新推回用户。

StarBridge提供资料、代码复用、执行、会话、状态与结果获取等通用支持；理解问题、决定方案、解释物理结果和规划研究由AI及其其他工具负责。特定类型算例的完整流程指导属于更远期目标，不要求StarBridge包办仿真研究。

### 2. 以完整Java API为正常工作方式

目标是通过STAR-CCM+ Java API和宏完成全部算例操作相关功能，不以已封装的工具、适配规则、模板或已做案例限定范围。遇到新的操作，不应总是等待开发者增加专用接口，也不应要求用户逐项发现并推动修补功能缺口。

可以保留真正减少复杂性的辅助方法，但不能让它们成为使用Java API的必经前提。不能只提供一个执行入口，就声称已经满足资料、编写、复用和结果获取的要求。

### 3. 显著降低完成实际任务的总成本

评价范围包括资料查阅、上下文读取、对象关系理解、代码编写与修正、客户端启动与连接、算例加载、执行、结果获取和解释。不以单次宏耗时、工具数量、记忆条数或少数成功案例替代整体效果。

应优先复用仍适用的知识、宏、代码片段和辅助方法；连续操作复用同一已加载算例，集中完成明确的读取、判断、修改和回读。需要AI根据新信息作决定时保留交互，不为了合并请求而扩大操作范围。

### 4. 同时支持GUI协同和后台独立工作

AI应能接手用户已经在GUI中打开的算例，也能在没有用户持续打开GUI的情况下独立处理任务。面向用户呈现的对象与操作位置应能对应STAR工作树、属性栏或菜单，但不要求重建整个界面。

不把完整算例副本作为默认前提；区分内存修改、覆盖保存、另存任务产物及额外保护副本。不擅自覆盖原文件、删除求解数据或丢弃未保存状态。

### 5. 保持资料与结果可靠

资料应来自用户实际使用版本，并按任务提供必要的签名、说明、继承和来源。查询不到不能直接等同于API不存在；不完整或未核实的信息应明确标识。

结果要区分空值、缺失、失败、局部读取及完整读取，也要区分完成、部分完成、失败和未知。编译通过不等于执行成功，宏返回不等于任务完成，任务完成不等于仿真物理可信。未知操作不能盲目重复执行。

### 6. 让经验在后续任务中真正发挥作用

工作记忆应同时保存问题、适用条件、代码或方法、来源、已有依据、效果和例外。复用的是方法，不是照搬旧算例的对象标识、名称和参数。

记忆可以来自实际操作、排错、资料研究和用户纠正；不要求用户逐条传授，也不为标记“已验证”而额外启动验证。相关任务中应能检索、审阅、使用并按新事实修订。

### 7. 不受既有实现牵制，也不无休止扩展

应按需求判断保留、替换或删除现有实现，必要时允许彻底重构；优先利用真正可取得且适用的官方或第三方能力，避免重复建设。

用户要求以完整、多样的实际生产力场景反复检查，而不是交付少量工具和案例后宣称完成。用户随后要求控制已投入的额度、先取得可用结果；因此当前已交付可用基线并暂停自动继续，不把暂停误报为总体目标完成。

## 二、当前可用基线

| 已可用的能力 | 当前范围 |
| --- | --- |
| 通用宏执行 | 代码方法体与原样完整宏可混合执行，支持同一请求内读取、判断、修改和回读。 |
| 完整宏复用 | 保留package、私有方法和原宏结构，显式附带辅助Java源码和JAR；不要求逐功能适配。 |
| 会话与生命周期 | 后台新建或加载、复用已有算例、接手本机GUI会话、显式保存/另存、区分外部断开和自有服务停止；不默认复制整个算例。 |
| 执行依据 | 源码与依赖冻结、预编译、逐步持久凭据、相同请求不重复执行、按需读取日志及编译材料。预编译成功后，STAR只编译薄启动器，不再重复编译用户程序。 |
| 资料与记忆 | 实际安装API与指南查询、同类多成员集中读取、记忆检索/读取/修订与部分方法复用。 |
| 按需入口与GUI位置 | 默认三个MCP入口，再展开所需方法；可取得标准GUI树路径及部分属性/菜单标签。 |

实际工作已包括通道建模、网格与连续工况求解，生产翼型设置比较，既有历史37帧翼面压力导出，以及8640条完整已存Cl—时间数据核对。这些证明相关工作已经做过，不证明全部功能和异常路径已覆盖。

完整连续任务主要集中在2602；2510有基础接入、保存、字段配置及编译/资料依据，不具备同等完整任务覆盖。历史任务使用过不同阶段的实现，不能把旧运行记录全部算作最新加载器的运行依据。详细范围见[通用执行说明](<../tech/generic-execution.md#当前实际证据与未完成项>)和[会话验证边界](<../tech/bridge-session.md#验证边界>)。

## 三、当前还需改进的问题

### 1. 任务准备和复核成本过高

**问题：**即使原生执行较快，AI仍需花大量时间查API、理解对象关系、拼接方法、编写任务检查及整理结果。前一轮截至成本记录时，混合开发、研究、准备和分析已超过110分钟，新增任务Java片段547行，还发生准备阶段与派发前的重复预编译；两次约7秒的execute不能代表整任务成本。

**影响：**用户已经付出较多额度，但得到可复用成果的速度和成本没有达到预期。一部分开销来自执行支持不足，另一部分来自AI分工、范围控制和交付节奏，不应全部归咎于STAR启动慢。

**改进方向：**减少重复研究和无必要的准备阶段编译，优先使用已有材料与方法，并在真实任务中区分准备、连接、执行和结果处理成本。成本记录见[实际任务成本](<../../outputs/requirements-first/history-handoff/task-cost.json>)。

### 2. 代码和方法复用仍需过多手工衔接

**问题：**完整宏及其依赖可以复用，但纯代码步骤尚不能直接附加顶层辅助源码/JAR；某些helper组合仍需增加完整宏入口，或放入`declarations`。参数、当前对象、辅助方法和返回结果之间仍存在手工拼装。

**影响：**已有可靠代码并不总能直接用于新任务，AI仍可能重复抄写和研究。辅助源码直接复用扩展尚未完成，已从交付代码撤回；保存的[未完成补丁](<../../outputs/requirements-first/usable-f7eef68/unfinished-helper-dependencies.patch>)不是可直接应用的成品。

**改进方向：**让现成Java辅助代码和任务代码自然组合，复用操作方法而非旧对象值；不以增加专用算例接口代替通用复用。具体实现方案需要届时重新核对。

### 3. 资料和记忆能查到，但未必能低成本找到并应用

**问题：**指南搜索主要利用标题与摘要索引；独立宏、辅助源码等材料的发现和定向读取仍不统一。跨进程缓存、重复读取及全局扫描仍有成本，记忆存储也存在全量扫描问题。短摘要不保证总是比直接读取原记录更省。

**影响：**AI可能重复查询已经获得的信息，或者虽然找到旧经验，仍需从头研究并改写。

**改进方向：**改进相关材料的检索、定向获取和有效信息复用，保留版本、来源、适用条件与不确定性，避免默认灌入整个文档库或记忆库。不得把语义检索、特定数据库等尚未决定的实现方式写成既定需求。

### 4. 连续操作仍有启动和通信开销

**问题：**算例可以保持加载，但每次请求仍使用临时批处理客户端。保存流程仍有重复往返，初次发现/接入、累计凭据写入和大结果返回也有成本。取消重复编译只解决了其中一个环节。

**影响：**表面上一次工具调用，内部仍可能发生多次启动或通信；小操作较多时成本会累积。

**改进方向：**先减少不必要的重复启动、查询和往返，再评估是否需要更换执行机制；不预设必须采用常驻客户端，也不为了测量重复加载大算例。

### 5. 失败处理有基础，但继续工作的路径尚不完整

**问题：**已有逐步状态、未知结果保留、阻止盲目重发，以及部分中断、超时和迟到凭据的实际依据；但显式核对与继续机制尚未一致覆盖所有路径。结构化修改、保存等未知状态仍有缺口，新初始化/显式接受流程和复杂依赖也缺少相应实际依据。

**影响：**目前“可靠地停下来”比“方便且正确地继续工作”更完善。一次只读检查成功不能自动解除此前未知写入，也不能断言发生的修改已回滚。

**改进方向：**在已有凭据和当前实际观察基础上明确已完成、接受的状态、剩余工作和未知范围，统一恢复入口。SPI、嵌套源码宏、异步工作等应按真实任务逐步取得依据，不为凑覆盖构造无关场景。

### 6. GUI协同和呈现仍有范围限制

**问题：**已有接入GUI算例、在原窗口显示修改的实跑；也能读取官方标准树模型。但标准模型不等于另一窗口的当前选中项、自定义布局或所有子菜单，不能把几条对象路径当成完整GUI协同。

**影响：**用户可以理解部分对象和操作位置，但复杂交接仍可能需要额外定位与解释。

**改进方向：**围绕实际任务补齐必要的对象和操作对应关系，明确观察的是标准模型还是实际窗口；该项优先级低于通用操作和主要维护问题，不重建整套界面。

### 7. 版本、依赖和交付环境的覆盖仍有限

**问题：**完整任务主要在2602进行，其他版本的已有依据较窄；复杂JAR/SPI、嵌套编译和异步加载没有同等覆盖。当前启动配置针对本机Linux环境，迁移机器仍需调整环境和路径。

**影响：**不能把本机可用直接推广为所有版本、平台和依赖组合都可用。执行声明也不是代码沙箱，不能自动证明任意用户宏没有其他副作用。

**改进方向：**优先服务用户实际版本和环境，随真实使用改进升级复用、依赖诊断和安装启动体验。区分历史实跑、当前编译和源码复核，不将缺少依据写成已验证。

## 四、后续推进的建议顺序

以下是基于当前差距的建议，不是新增需求或已获准立即执行的方案：

1. **优先降低准备与重复编码成本。**让已取得的可靠方法能用于下一项实际任务，而不是继续增加工具和案例数量。
2. **改善资料、记忆与代码材料的实际复用。**减少重复查阅、上下文和手工拼装。
3. **减少连续操作的启动与通信开销。**以真实任务总成本判断效果，不删除必要身份检查或结果依据。
4. **补齐恢复和交付体验。**让用户能够可靠接手、继续或迁移工作。
5. **结合真实任务处理其余GUI、版本与依赖问题。**不为了把清单全部勾选而额外运行STAR。

当前没有约定新的额度上限、时间表或固定实现方案。本次只保存目标和问题记录；自动开发保持暂停。后续恢复时先核对代码、环境和已有材料的实际状态，再决定下一项范围明确的工作，不把本记录视为无限继续执行的授权。
