# 分发与首批 Harness 接入计划

状态：本地交付完成。P1、P2、P4 已交付；P3 按 2026-11-02 用户调整后的范围完成三端项目级安装接入验收，没有调用模型。外部发布尚未执行。具体证据与缺口统一见[分发说明](../distribution.md#验收状态)。

依据：[路线图](../roadmap.md#分发与-harness-接入) · [Skills 设计](../../StarBridge.md#skills) · [当前 MCP 接口](../tech/mcp.md)

## 目标与范围

用户可以安装指定版本的 StarBridge，并在所选 Harness 中接入 MCP、安装需要的 Skills，无需克隆源码仓库和手动配置仓库内 Python 脚本路径。首批支持目标为 Codex、Claude Code 和 DeepSeek Harness（下文简称 DSH），三者均需独立验收。自 2026-11-02 起，后续只验收这三个 Harness 的安装接入情况；不向模型发送提示、契约、Skill 或算例信息来执行任务。Cursor、OpenCode 及其他宿主不纳入验收范围。

Harness 指管理模型调用、上下文、权限和工具执行的 Agent 宿主。它是否能安装配置、是否能完成 MCP 通信、是否能执行真实 STAR 工作流，是三个不同的验证层次；上游安装器列出某客户端，不等于 StarBridge 已支持该客户端的全部功能。

本轮沿用 Linux 上的本机 stdio，记录操作系统、Harness、安装器和 StarBridge 版本及实际执行文件。安装验收不打开 STAR 算例、不执行读写或求解；已有真实 STAR 证据作为独立的历史记录保留。跨 Harness 支持不扩展操作系统、STAR 版本或算例操作范围。远程 HTTP 服务、Windows/macOS 运行适配、GUI 接入、网格／求解新工具和持久化记忆分别按后续需求推进。

## 分发方式

同一 Git 仓库维护程序和通用 Skills，通过不同入口分发；初期不拆出独立 Skills 仓库，也不为每个 Harness 复制业务实现。

| 交付内容 | 分发与安装入口 | 职责 |
|---|---|---|
| Core、Bridge、JSON CLI、MCP 与运行必需资源 | 一个 Python 发行包，发布到 PyPI；使用 `uvx` 或固定安装环境启动 | 提供实际执行能力，统一版本和资源 |
| 通用 Skills | 仓库的 `skills/<skill-name>/SKILL.md` 及附属资料；使用 `npx skills add` 或安装到宿主扫描目录 | 提供领域工作流、判断依据和验收步骤 |
| MCP 客户端配置 | 能通过 `npx add-mcp` 完成接入的统一使用该入口；必要的原生适配最多覆盖 Codex、Claude Code 和 DSH | 写入启动命令、参数、环境变量及宿主专属设置 |
| MCP 发现元数据 | `server.json` 与官方 MCP Registry | 指向实际发行包及启动信息，供目录和安装工具发现 |

`npx add-mcp` 是 MCP 配置的首选入口。能通过它完成接入的 Harness，不再另行交付或维护原生 MCP 安装命令、配置模板和独立安装路线。后续原生 MCP 适配范围最多限于 Codex、Claude Code 和 DSH，且仅在 `add-mcp` 无法满足必要接入要求时启用；这不是要求同时实现三套原生适配。其他 Harness 如遇安装器缺口，记录问题并等待上游支持，不新增项目维护的原生适配。

本文的“原生 MCP 适配”指绕过通用安装器、直接维护宿主命令或配置文件的接入方式，不改变 StarBridge 使用的 MCP 协议和 stdio 传输。官方 MCP Registry 保存元数据，程序仍由 PyPI 托管。初期不维护额外 npm 启动包装、自建安装器或插件市场。

### Python 发行包

新增 `pyproject.toml` 与稳定的 CLI、MCP 命令入口。PyPI 的 `starbridge` 已由其他项目使用，本项目发行包改用 `starbridge-cfd`，Python 包与 CLI 仍为 `starbridge`，MCP extra 为 `mcp`，服务命令为 `starbridge-mcp`。2026-11-01 查询 `starbridge-cfd` 未发现公开项目，这不是名称已保留的保证，发布前仍需核对。保留 Core／普通 CLI 的轻量依赖边界，MCP 所需依赖由 extra 声明。

预期启动形式如下，其中名称和版本均是发布前需要落实的内容，当前不可作为已可用安装命令：

```text
uvx --from 'starbridge-cfd[mcp]==<version>' starbridge-mcp
```

打包需包含受支持操作依赖的 Java 模板、目录、规则和 schema，解除对源码仓库根目录及调用者当前目录的依赖。运行日志、会话文件、生成缓存与用户算例写入明确的可写位置，不写入已安装的软件包目录。仅分发项目有权发布的运行资源；STAR 安装、许可证、Javadoc 和用户算例由执行环境提供，不随包附带。

已有 JSON CLI 与文件／会话入口的迁移方式需在实施时明确，避免包装过程改变工具契约。离线或受限网络环境可使用预先准备的固定版本环境和可执行文件路径，不能假定每次启动都能下载依赖。

### Skills

Skills 使用通用 `SKILL.md`、`references/` 和必要资源。首个代表性工作流已确定为 `starbridge-case-audit` 只读算例审查，当前内容见[Skill](../../skills/starbridge-case-audit/SKILL.md)。配置类 Skill 只组合已验收的写入能力，不因发布工作流而扩大工具范围。

Skill 通过服务身份、工具说明及当前契约使用 StarBridge，不固定某个 Harness 加工后的工具名前缀。通用内容不依赖专属 hooks、子代理机制或宿主插件清单；确有必要的专属设置作为薄适配层维护。Skill 不重复维护 Java API 绑定、完整参数 schema 或 STAR 精确版本列表，也不保存可复用的会话句柄和旧 `expected`。

安装 Skill 与接入 MCP 是两个步骤。Skill 被加载后应能识别工具未连接、契约版本不兼容或能力缺失，并明确指出原因。MCP 自身仍须支持不依赖 Skill 的明确任务。

## 接入原理与运行位置

安装时，Skills 工具将工作流放入宿主识别的目录，MCP 配置入口将同一个服务启动命令转换为宿主所需的配置格式。安装器不参与后续工具调用。

运行时，Harness 按配置启动 StarBridge，读取 MCP 工具说明，将模型选择的调用通过 stdio 发送给服务。共享 Core 和 Bridge 执行实际 STAR 操作，再将结果返回 Harness。Skill 按需进入模型上下文，指导工作顺序；实际预期状态检查、写入条件、回读与保存规则仍由 StarBridge 执行。

首批本机部署要求 MCP 进程所在环境能够访问 STAR 程序、许可证和算例路径。IDE 的远程工作区或云端 Harness 可能在另一台机器启动进程，不能仅因桌面端已安装就认定执行环境具备这些条件。仅提供远程 HTTP 接入的宿主不属于本计划直接覆盖的本机方式。

## 首批 Harness 接入安排

下表记录交付目标，不是现有验收结果。具体路径和上游行为依据 2026-11-01 查询的官方资料；实施时按选定版本再次核对。产品名相同的 CLI、IDE 和桌面形态须分别记录，不能继承彼此的验收状态。

| Harness | MCP 接入安排 | Skills 接入安排 | 首批验证对象与当前状态 |
|---|---|---|---|
| Codex | 使用 `npx add-mcp` 的 `-a codex` 目标；必要接入要求无法满足时才考虑原生适配 | `skills -a codex`；核对项目／用户作用域 | Codex CLI 的安装接入；具体版本与结果见分发说明 |
| Claude Code | 使用 `npx add-mcp` 的 `-a claude-code` 目标；必要接入要求无法满足时才考虑原生适配 | `skills -a claude-code`，安装到 `.claude/skills/` 或用户目录 | Claude Code 本地安装接入；无需模型登录 |
| DeepSeek Harness | 当前安排在 profile 中配置 `@deepseek-ai/dsh-mcp-client` 并交付原生模板；若实施时 `add-mcp` 已满足接入要求，则统一改用安装器 | 通过文件系统 Skill provider 使用项目 `.agents/skills/`、`.dsh/skills/` 或用户 `~/.dsh/skills/` | 官方 DSH 插件和 Skill provider；记录实际安装版本 |

表中 `skills -a` 和 `add-mcp -a` 仅表示安装工具的目标参数，完整命令随最终包名、版本和已验证配置一并交付。安装说明需明确项目／用户作用域，保留已有无关配置，并说明更新、移除和回退方式。

当前及后续验收仅限上述三个 Harness，不因安装器支持其他宿主而扩大范围。

### DeepSeek Harness 的专门安排

DSH 官方 MCP client 已提供 stdio、工具调用、服务 instructions 和资源读取，足以作为现有 StarBridge 的接入基础。当前查询的 `add-mcp` 与 `skills` 目标列表没有 DSH 专用项，因此暂按原生 MCP 配置与现有 Skill 目录安排。实施前先复核安装器支持情况；若 `add-mcp` 已能完成必要接入，则采用安装器，不再维护并行原生路线。以下原生配置安排仅在该缺口仍存在时执行，不以第三方 DSH 桌面封装的配置格式代替官方 Harness 配置。

MCP 模板使用 `serverName: starbridge`、`transport: stdio` 及已确定的程序命令。实施时核对所选 profile 是否已具备工具注册表、资源服务和必要插件，按该版本的原生机制添加配置，不重复挂载服务。

Skill 文件系统 provider 默认识别项目 `.agents/skills/`，因此项目级 `skills --agent universal` 可作为待验收的便利路径；`universal` 当前的全局目录 `~/.config/agents/skills/` 与 DSH 默认用户目录不同。全局安装优先使用 `~/.dsh/skills/`，或显式设置 `customSkillDirs`，不宣称全局通用安装自动生效。Skill 目录直接采用 `<skill-name>/SKILL.md`，避免 DSH 不扫描的额外嵌套层级。

DSH 默认 `toolCallTimeoutMs` 为 60,000，且会清理继承给 stdio 子进程的部分环境变量。模板应说明如何按 STAR 操作耗时设置更长超时，并显式传入执行所需的环境；不把某个示例超时当作所有任务的上限。启动协商可能先创建探测进程，再创建服务进程，因此服务启动不能自动加载算例或触发写入。断线重连不等于恢复或重放未完成的修改，必须沿用 StarBridge 的状态查询与不确定结果处理规则。

## 版本与发布关系

每次发布提供一份兼容关系：Python 发行版本、MCP 契约版本、对应 Git tag 的 Skills、Skill 所需最低契约与能力，以及经过安装验收的操作系统和 Harness 版本；已有 STAR release／Build 的能力验证范围单独引用。初期程序和通用 Skills 在同一 Release 中给出可复现的配套版本；安装后可以分别更新，但必须核对兼容关系。

正式 MCP 配置固定发行版本，升级显式执行。Skill 安装需提供可定位到发布 tag 或提交的来源方式，不能只以浮动主分支代表已验证组合。程序回退只改变运行版本，不暗示已修改的算例状态自动恢复。客户端更新或 DSH 插件变化实质影响配置时，先核对受影响项，再更新支持记录。

发布物包括 Python wheel／源码包、同版本 Skills 来源、三个 Harness 的接入说明与适用的 `npx add-mcp` 命令，以及 Registry 元数据。原生 MCP 模板仅为安装器无法满足必要要求且位于上述三者范围内的目标提供。最终发布前核实包名、Registry 身份和工具对 Python extra／启动入口的表达方式。MCPB 桌面安装包和宿主专属插件包留作后续便利渠道，不作为首批依赖，也不用于绕过原生适配范围限制。

## 验收范围

2026-11-02 用户明确将本轮及后续 Harness 验收收窄到安装接入。只发送本机配置、初始化、状态、工具列表和无会话契约请求；不发送模型 user 消息或启动模型 turn，不以模型登录作为完成条件。已有验证脚本优先复用，不扩展全库测试。

| 验收对象 | 必须确认的结果 |
|---|---|
| 发行包与入口 | 固定版本环境的命令可启动，运行资源完整，源码目录外可取得契约；不依赖 STAR 运行 |
| 配置安装 | 在明确的项目或用户作用域，通过选定入口生成并加载配置；Codex、Claude Code 统一使用 `add-mcp`，DSH 仅在安装器缺少目标时使用原生插件片段；保留无关配置 |
| MCP 连接 | 每个宿主或其官方 MCP client 完成真实 stdio 握手，确认 StarBridge 身份与工具列表；可用控制接口取得契约时直接查询，不由模型执行 |
| Skill 安装 | 同一 Skill 安装到该宿主扫描目录，实际枚举到名称和说明；文件与发行来源一致；支持本机 provider 加载时可直接读取，不调用模型 |
| 安装维护 | 选定作用域的更新、移除和恢复不影响无关配置；相同安装器版本已有证据可复用，不要求制造未发布版本来演练回退 |
| 结果边界 | 记录版本、执行文件、作用域及缺口；区分隔离项目安装验收与用户日常配置，不能将前者宣称为后者已经安装 |

三个目标满足上述安装范围后可完成 P3。用户级和项目级不要求重复验收全部组合，但未实测作用域必须标明。安装检查不等于模型能执行 Skill，也不证明真实 STAR 读写、超时恢复或 CFD 物理有效性；这些均不再作为跨 Harness 安装验收的完成条件。历史模型和 STAR 验收证据保留在分发说明，不因本次范围调整改写为安装证据。
