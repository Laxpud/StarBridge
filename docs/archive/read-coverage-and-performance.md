## 1. 建议结论

优先采用两条相互配合的改进路线：

1. **以对象实际身份和属性语义选择读取能力，不再由定位入口独占读取器。** 先补几何选择、对象引用与坐标，再复用已核验的目录读取管线，保留完整的版本、成员声明和实例条件约束。
2. **减少 STAR 客户端往返，而不是缓存当前值冒充新读取。** 在已有有效契约时，把描述符／身份核验和读取合并到一次客户端请求；再增加有界多对象只读批量，最后依据分阶段测量决定是否需要常驻客户端。

不建议第一步重写全部对象系统、自动调用所有 getter、放开隐藏属性，或直接引入常驻 Java 服务。下面的接口形状和字段都是候选设计，不是已发布契约。

## 2. 源码已经确认的原因

### 2.1 统一了接口外形，尚未统一能力选择

[对象引用解析](<../../src/starbridge/core/objects.py#L12-L37>)仍区分 runtime 和 catalog 来源；[Service 读取分支](<../../src/starbridge/core/service.py#L258-L268>)据来源选择执行器。运行时引用不能直接转换成目录 target，这是当前身份保护，而不是应当删除的多余校验。

因此，同一 Velocity 对象通过树入口只得到通用 Bean 规则，通过目录入口则得到专门适配的 Profile 读取管线。仅修改公开方法名或让客户端自动改用另一个 ID，并未解决这种能力分裂。

### 2.2 通用读取规则的类型集合较窄

[发现策略](<../../src/starbridge/core/discovery_policy.py#L7-L41>)只登记基础值、标量 input、向量 input 和枚举 input；[规则选择](<../../src/starbridge/core/discovery_rules.py#L37-L58>)对未命中类型返回 `unsupported_value_type`，对隐藏属性先返回 `hidden_property_metadata_only`。

另一方面，[Java 编码器](<../../src/starbridge/bridge/java/CatalogRuntime.java#L1850-L1905>)已经具备 reference、collection、query、java_class 等适配能力。问题包含“已有底层能力未接入发现规则”，不能一概解释为 Java 无法读取。

不过，现有 query 编码器只接受 `ManagerWithQuery`，**不能把 `DynamicQuerySelectorInput` 直接标为 query 就算完成适配**。

### 2.3 非 CSO 代理在导航层即被挡住

[发现提供器](<../../src/starbridge/bridge/java/DiscoveryRuntime.java#L74-L126>)仅给 `ClientServerObject` 子对象分配真实对象身份；其他子对象保留代理元数据。它们没有 CSO key，不能通过伪造 key 或沿用列表下标变成普通对象。

### 2.4 一次运行时读取通常产生两次 STAR 客户端执行

当前顺序是：

```text
read_properties(runtime object)
  → prepare_node_read
    → describe_node
      → 客户端 A：连接、描述、退出
    → 本地校验 Javadoc、准备读取计划
  → 客户端 B：连接、校验绑定、读值、退出
```

依据：[读取准备](<../../src/starbridge/core/discovery.py#L321-L355>)、[读取执行](<../../src/starbridge/core/discovery.py#L386-L407>)、[每请求启动客户端](<../../src/starbridge/bridge/runner/file_bridge.py#L198-L244>)。

前面刚调用过 `describe_object`，后面的读取仍会重新描述。已有[Java 辅助类编译缓存](<../../src/starbridge/bridge/runner/java_runtime.py#L40-L77>)、[Javadoc 元数据缓存](<../../src/starbridge/core/discovery_rules.py#L88-L105>)和[计划缓存](<../../src/starbridge/core/discovery_rules.py#L202-L213>)不会消除这两次连接与短生命周期客户端执行。

### 2.5 部分错误信息在读取结果中变粗了

描述能提供 `unsupported_value_type` 或 `hidden_property_metadata_only`，但[读取结果组装](<../../src/starbridge/core/discovery.py#L386-L420>)把不支持项统一成 `unsupported_property`。这不造成假值，但使调用者难以判断该补适配、换能力来源还是尊重策略禁止。

## 3. 读取能力改进：分层，不堆对象名称特例

### 3.1 第一层：补充有边界的通用值类型

| 读取族 | 解决的本轮缺口 | 必须保留的信息和约束 |
|---|---|---|
| STAR 对象引用 | 坐标系、Representation、ProfileMethod、Units 等 | 名称、实际类、会话身份；null 与失败分开；不递归读取整个关联对象 |
| 静态／动态选择器 | Airfoil GeometryObjects、Cl Parts、其他对象选择 | 选择模式、配置、实际结果的独立状态；未知查询不能变成空列表 |
| 坐标 input | BackgroundBlock Vertex1／Vertex2 | 原始分量、逐分量单位、坐标系、表达式及可核验的数量关联 |
| 有类型的集合 | ManagedCoordinateSystems、ContactingParts、DescriptionsOutput 等候选 | 实际返回类型和元素契约分别核验；预算、分页、逐项失败、顺序语义 |
| Dimensions／具体选项对象 | Velocity DimensionsVector、PressureOption 等 | 文本、量纲指数、选项枚举分别定义，不能互相冒充 |

这里列的是适配目标，而不是声明这些字段都可用同一 getter 读取。每族仍需精确 Build、公开成员签名／指纹、声明与运行时类型检查、null 和错误规则。当前 `CoordinateSystem` 等关联可优先复用 reference 编码；是否扩大到整个 CSO 子类体系，应以继承关系和只读规则核验为前提，不能仅按类名后缀判断。

集合不能全部照搬当前排序输出：若原 API 有顺序含义，应保留顺序并说明；若是选择集合可规范化排序用于比较。大型集合的输出限额不等于底层读取限额，必须说明是否已全量物化；若 STAR 没有真正有界的访问入口，不能宣称分页限制了求值成本。

新增读取能力默认只读。现有写入规则迁移、expected 格式和新值 schema 不应因为读到了新对象类型而自动扩权。

### 3.2 Airfoil 选择器：同时定义“选择配置”和“当前解析结果”

#### 官方 API 已确认的限制

[DynamicQuerySelectorInput 本机文档](</opt/Siemens/21.02.007-R8/STAR-CCM+21.02.007-R8/doc/client/html/star/common/DynamicQuerySelectorInput.html#L443-L524>)说明：

- `getQuery()` 取得动态查询规则，`hasQuery()` 判断是否有查询。
- `getSelectedInstances()` 在存在 query 时会抛 `NeoException`。
- `getManager()` 带 `@Internal`，不应为了便捷解包绕过当前禁止策略。
- `applyTo(...)` 会把选择／查询应用到 manager，属于修改，不能用于读取。

[CustomMeshControl 本机文档](</opt/Siemens/21.02.007-R8/STAR-CCM+21.02.007-R8/doc/client/html/star/meshing/CustomMeshControl.html#L395-L423>)公开了 `getGeometryObjects()` 和 `getObjectsOnWhichControlApplies()`。这些可作为专用只读适配候选，但仅靠签名尚不足以证明其求值成本、无副作用以及与 GUI 所选对象的精确对应。

#### 推荐读取语义

1. **静态选择**：核验无 query 后，从已核验的选择器入口读取显式对象引用；空列表只有在成功、完整读取时才表示没有选择。
2. **动态选择规则**：复用并适当拆分现有 query/predicate 编码逻辑，返回规则、modifiers 和规则读取状态，不把当前匹配集合当作规则。
3. **当前匹配对象**：通过拥有者的已核验公开 manager／关联入口读取；在实现前确认得到的是查询当前结果，而不是所有候选对象。不能用 input 的内部 manager，也不能先修改 query 再读取。
4. **实际作用范围**：选择结果、经过控制条件过滤后的作用对象、最终网格影响是三件事。`ApplyOnlyToContact` 等条件可能相关，未核实就不能把“选中了表面”写成“网格已经受控”。
5. 规则和解析结果分别报告 `ok / unsupported / error / not_requested / partial` 等状态；具体枚举由正式契约确定。未知 predicate 可保留其类型和失败原因；如果另一条已核验路径能取得当前对象，仍可返回对象结果，但整体不能冒称规则已完整读取。
6. 昂贵的动态解析由显式读取项或选项触发，不放进 `describe_object`。针对本次审查，应明确请求规则和解析结果，而不是默认全树求值。

[现有 query 实现](<../../src/starbridge/bridge/java/CatalogRuntime.java#L2281-L2338>)在静态模式返回对象，动态模式只返回 predicate 和 modifiers；因此仅复用它仍不足以回答“现在选中了谁”。优先复用谓词编码能力，再单独实现拥有者相关的结果解析。

### 3.3 第二层：复用已接受的目录读取规则，而不是自动换对象

建议建立内部 `ReadCapability` 注册与组合层，包含：精确版本、允许的接收类型、getter／转换管线签名、返回值 schema、只读证据、实例条件、预计成本类别、是否需要拥有者上下文和能力来源。

选择顺序：

1. 执行显式禁止与版本检查；安全禁止不能被 fallback 绕过。
2. 按精确声明和实例条件选择已审查的专用读取规则。
3. 否则采用已支持的通用值类型规则。
4. 仍不支持时保留具体原因及可用的替代能力提示，不启动第二套全树扫描。

关键设计约束：

- 不按 `Velocity`、`Airfoil` 等显示名称推断规则；按声明 owner/member、版本、类型和拥有者关系匹配。
- 对对象自身 getter 的纯只读管线，可以在当前树对象上执行，不必先调用 `find_objects` 重新定位。
- 依赖目录 parent 的规则必须证实真实业务拥有者。树里的直接父对象可能是 `PhysicsValueManager`，而目录 parent 是 Boundary，不能直接替换二者。
- 只有在拿到同会话真实 object key 后才能认定两引用指向同一 CSO；名称、类名和相似路径不能证明同一对象。短期可保留两种定位材料，能力选择先独立于来源；不必为补读取立即强制迁移全部 ID。
- 属性语义显式映射，不只按名字去重。例如 `Method` 与目录 `method` 可在核验后对应；`DimensionsVector` 与目录 `dimensions` 文本不能被当成等值替身。
- 对已经公开的属性 ID 不静默更换值结构。新增语义项或声明兼容别名；若必须破坏 schema，则明确版本迁移，不沿用旧写入 expected。
- 读到关联引用后可支持受控继续定位，但不默认递归展开。关联对象可能不在普通所有权树中，需要返回真实 relation 定位材料，不能拼一条不存在的树路径。

项目已有[接受写入规则迁移机制](<../../src/starbridge/core/discovery_write.py#L106-L140>)可借鉴“按完整管线签名匹配”的结构，但读取复用不等于调用写入迁移逻辑，也不继承 setter 权限。

### 3.4 第三层：非 CSO 代理用专用提供器处理

[DirectedMeshSourceSurfaces 文档](</opt/Siemens/21.02.007-R8/STAR-CCM+21.02.007-R8/doc/client/html/star/sweptmesher/DirectedMeshSourceSurfaces.html#L178-L228>)有公开的 `getSourceSurfacesInput()`、`getSourceSurfaces()`、`getOperation()`。这表明缺口有可研究的只读入口，但不是已经完成实例验证。

建议优先为源面／目标面这两个实际需要的类型注册代理提供器：

- 以“拥有者会话身份 + 提供器类型／角色”定位视图；每次从已核验拥有者重新取得唯一候选，并核对其 `getOperation()` 关联。
- 不使用 `proxy_ordinal` 作为稳定身份，不伪造 CSO key，不开放任意反射方法。
- 若无法证实角色唯一或与拥有者绑定，继续返回不支持。
- 可先把源面／目标面选择作为 MeshSliding 的专用只读属性提供，解决诊断需求；后续确有导航需求时，再公开代理视图引用。
- 代理与动态选择适配共享值编码，但导航身份必须独立设计。

### 3.5 隐藏属性保持逐项审查

本次两个隐藏属性分别为 double、boolean，却仍不可读，原因是策略禁止而非值编码。不能把 `DENY.hidden` 全局关闭。

若业务确实需要，按精确 owner/member/Build 审查 API 和必要的实现证据、当前模型适用性及副作用，再发布显式只读规则或受控例外。内部／废弃标记和写入权限仍独立约束。数值读到了也不自动证明该设置当前生效。

### 3.6 坐标不能退化成三个没有上下文的数

[CoordinateInput 文档](</opt/Siemens/21.02.007-R8/STAR-CCM+21.02.007-R8/doc/client/html/star/common/CoordinateInput.html#L344-L427>)同时公开坐标系、定义、向量、逐分量单位。新适配器应保留这些语义，不能简单当作已有 `VectorPhysicalQuantityInput`：非笛卡尔坐标可能包含角度分量。

第一阶段返回原始坐标及其单位／坐标系，不做隐式坐标变换。若以后需要统一到 Laboratory，作为另一个明确操作或读取视图，说明转换依据并单独核实。

## 4. 性能优化：先减少往返，再优化单次开销

### 4.1 先建立分段计时与调用次数证据

建议同一请求记录以下阶段与缓存命中：

- 会话锁等待；描述／定位；Javadoc 加载与校验；计划准备。
- 辅助类缓存命中、必要编译；请求宏生成；客户端启动与连接。
- Java 内目标解析、描述核验、属性读取、动态查询求值、编码。
- 客户端退出、结果解析、引用登记和输出持久化。
- `client_launch_count`、读取属性数、对象数、返回字节数、是否截断。

目前 Java `elapsed_ms` 只计发现函数内部，不能定位剩余 5 秒具体花在哪个阶段。源码能确认短客户端和双请求结构；具体耗时比例仍待测量。已有证据不支持先把瓶颈归结为 Javadoc、磁盘或网络。

### 4.2 第一优先：有契约的读取走“一次客户端校验并读取”

推荐快路径：

```text
有效的描述／只读计划缓存
  → 本地准备经验证的固定读取计划及期望描述签名
  → 一次 STAR 客户端请求
    → 核对 Build、session token、Simulation 和对象身份
    → 刷新并核验选定属性的描述符／接收对象类型
    → 契约仍匹配才读当前值
    → 返回值、逐项状态、观察区间与失效信息
```

这不是取消描述核验，而是把当前单独一次客户端执行的核验合并到读值请求中。首次发现或缓存未命中仍可能需要两次请求。

需要明确：

- 核验范围包括隐藏／禁止／getter 签名／运行时类型和与属性 ID 相关的语义上下文，不能只比较名称。
- 对象删除重建、parent 改变、模型／方法改变导致契约失效时，不执行旧 getter 管线。返回 `schema_changed` 等明确状态；只读可按明确恢复流程重描述、重编译，不能无界自动重试。
- 计划只能来自服务器生成并核验的注册能力，调用方不能传入任意 Java 调用。
- 保留同会话串行锁；GUI 可独立变化，因此一次宏内顺序观察也不等于数据库原子快照。提供观察区间和必要的前后身份／指纹检查，不承诺全算例同时刻一致。
- 这轮优化只覆盖读取；写入链必须继续执行完整 expected、实例条件、setter 次数和回读规则，不借机弱化。

可验证的结构目标是：已有有效契约、身份未变化时，把一次运行时读取的客户端启动次数从 2 降到 1。参考本次约 11 秒与约 5–6 秒的单请求耗时，预期能减少一轮固定开销，但具体秒数、收益比例不能在实施前保证。

### 4.3 第二优先：有界多对象只读批量

现有 `read_properties` 已支持同一对象多个属性；[计划合并](<../../src/starbridge/core/discovery.py#L358-L383>)也避免同对象局部编译降级后启动多个客户端。不应把这些已有能力再次包装为新优化。

真正新增的收益在于：把已定位的多个对象放进一次顺序执行的只读请求，共享版本检查、连接、公共父路径解析和请求内去重。要求：

- 每项有独立结果，不因一个对象不支持而丢弃其余结果。
- 明确对象数、属性数、集合规模、时间和输出预算。
- 同会话 Java 访问顺序执行，不用并发调用 STAR 对象来掩盖延迟。
- 只读批次不混入修改、保存、网格和求解。
- 动态选择规则默认按需求值，不因批量请求扩展为全树检查。

已知深层路径还可考虑一个有界的路径解析请求，返回实际唯一定位，不凭名称猜对象；这可以减少逐层对话往返，但不应默认全树 BFS。

### 4.4 缓存什么，不缓存什么

| 内容 | 建议 |
|---|---|
| 安装 Javadoc／成员声明 | 缓存，键包含实际安装、Build、文档修订证据或指纹与规则版本 |
| 通用编译计划／Java 辅助类 | 缓存，以代码、规则、运行库与版本指纹失效；不夹带会话 key |
| 描述快照 | 可供准备计划使用；TTL 不是实例仍有效的证明，执行时仍核验 |
| 实例引用 | 按 session token 与真实 key 隔离；不跨重载；关系变化须拒绝旧绑定 |
| 当前属性值 | 不把上次结果作为本次实时读取；如未来提供历史观察模式，必须明确标记且不能作为写入 expected |
| 动态选择解析结果 | 默认不跨请求缓存；否则可能遗漏 GUI 修改、标签变化或几何变化 |
| 请求内重复 getter／公共父路径 | 可在明确共享观察语义和身份核验下复用，避免同批重复访问 |

当前缓存机制已经不少，优化重点是验证并改善命中和失效条件，而不是再加一层不透明缓存。特别是安装路径不变时原地更新文档／库的情况，需要明确失效依据。

### 4.5 结果精简和本地 I/O 属于后续优化

[引用登记](<../../src/starbridge/core/discovery.py#L44-L84>)为每个对象开 SQLite 连接，[浏览缓存](<../../src/starbridge/core/discovery.py#L175-L185>)逐对象写 JSON，可在大集合下评估事务批量化、按变化写入等优化。但本次单层 Java 内部几十毫秒与端到端数秒的差异，尚不足以证明本地 I/O 是主因。

描述可按需返回精简能力／详细 Javadoc 元数据；完整结果仍可另存。精简不得删除错误、分页、范围、来源或会话恢复信息。读取失败需保留具体原因，避免用户再描述一次才能解释错误。

### 4.6 常驻客户端作为后续选项，不是首轮前提

如果减少请求轮数、批量和缓存后仍无法满足实际延迟要求，再验证常驻客户端是否受当前 STAR API 支持。它可能消除每次进程启动，但会引入连接断开恢复、模型线程安全、会话身份、请求取消、外部 GUI 共存、许可证和退出语义等额外成本。

不能把 Python MCP 常驻、STAR 求解服务常驻、Java 请求客户端常驻当成同一回事。当前前两者可以常驻，并不意味着第三者已经复用。也不能通过暴露任意远程 Java 执行接口实现所谓加速。

## 5. 完整性与生命周期必须一起改善

### 5.1 不要只用一个 complete 表达所有层次

保留现有请求范围完成语义，并补充兼容的覆盖说明：请求了什么、支持／失败／未请求什么、选择规则和解析结果分别是否完成、截断在哪一层。

任务级结论由审查层判断：例如“核实 Airfoil 控制”至少需要开关、选择配置和所需解析结果；读取到开关不能自动得出控制有效。没有目标清单的普通属性读取，不必因为对象上存在任意辅助不支持属性就永远标为失败。

### 5.2 只读即脏需要独立定位，不能用关服策略掩盖

后续调查应分阶段记录：加载后最早可观察的 modified、第一次 session-info 前后、描述前后、值读取前后及最小快照前后；同时记录桥接写入动作数和会话所有权。最早的桥接观察本身也可能包含初始化，必须清楚标明观察时点，不声称拿到了不可观测的“加载前状态”。

当前已知是打开返回时为 true，不能断言由任何新增 getter 造成。扩大读取适配时尤其要核验惰性初始化和物化行为；公开 getter 存在不等于已证明无副作用。

关闭拒绝时应给出明确错误码与恢复选项，不自动保存，也不因为桥接写入次数为零就自动 discard。用户已有会话只断开；本工具自有会话的丢弃仍需显式授权。

## 6. 推荐实施顺序与验收边界

下面是未来实施的验收要求，不是本轮编写或已执行的测试。

| 阶段 | 工作 | 退出条件 |
|---|---|---|
| A：证据与基础边界 | 保留具体不支持原因，补运行构建标识与分阶段计时；确定新增选择结果契约 | 能区分未适配／策略禁止／实例失效，能统计客户端次数；不改现有值语义 |
| B：关键读取覆盖 | 优先 Airfoil 静态选择、动态规则与有界解析；补 reference 和坐标；注册所需专用规则 | 在实际相应场景中区分空选择、非空选择、动态匹配、未知 predicate 与失败；单位／坐标系不丢失 |
| C：能力复用与一次读取 | 让树对象使用匹配的已接受读取规则；有效契约下同一客户端核验并读值 | 同一对象的已对应属性不因入口不同而不可读；热路径一客户端，旧身份／描述变化拒绝 |
| D：代理与批量 | 源面／目标面专用提供器；有界多对象只读批量 | 不伪造代理身份；局部失败可见；同会话顺序执行；明确预算和观察一致性 |
| E：定点完善 | 审查两个隐藏字段；调查只读 modified；依据计时再评估常驻客户端 | 不通过放开全局禁止、自动保存／丢弃或旧值缓存制造表面成功 |

阶段 B 和 C 可以拆成小改动交替推进：先以 Airfoil 和 Velocity 两个真实案例打通最小完整链路，不必等通用框架覆盖所有 STAR 类型。架构上保持能力注册与定位分离，避免为每个 GUI 节点增加名称特例。

未来验证还应覆盖同名不同对象、删除重建、父关系改变、模型／方法切换、跨会话旧引用、null、截断、未知子类和读取错误。真实性应以新会话实际对象和值为依据；不要把模拟覆盖或 Javadoc 签名核验标成真实 STAR 成功。

性能对比应固定安装、源码、算例、对象、属性集合和并发条件，分别记录冷／热请求、多次样本、客户端次数、返回量及失败率；报告中位数和分位数时注明样本量。第一验收指标是等价证据下减少请求次数，而不是预先承诺一个毫秒数。
