## 实施顺序

| 顺序 | 实施安排 | 任务入口 |
|---|---|---|
| 1 | 先调整会话连接、进程归属、保存语义及运行数据位置，为连续读写提供统一会话。 | [会话与存储](../../TODO.md#会话与存储) |
| 2 | 在会话状态中区分请求失败、忙碌和写入结果未确认；收窄普通赋值检查，替换签名引用。 | [状态与写入](../../TODO.md#状态与写入) |
| 3 | 复用类型适配与执行资源，减少计划文件往返和重复准备；迁移已有能力后移除旧接口与结果投影。 | [接口与执行](../../TODO.md#接口与执行) |
| 4 | 三端插件共用程序与 Skill，通过原生安装和更新入口交付；保留源码与通用接入。 | [插件交付](../../TODO.md#插件交付) |

第 4 部分的市场接入可以独立于第 3 部分尚未结束的接口迁移推进。减少客户端启动开销先从资源复用和请求合并入手，不预设常驻 RPC 架构。行为与存储约定以关联规格为准。

## 市场接入与安装验证

2026-11-03 的安装交付范围为第 4 部分，不包含第 3 部分的接口迁移。StarBridge 维护三端插件包，`my-awesome-vibekits` 维护统一 catalog 和三端生成索引。用户已授权两个仓库提交、推送和发布后 DSH 安装验证；该授权属于此次安装交付，不延伸为后续修改的提交授权。

安装验证使用隔离的客户端配置，只检查原生安装、MCP 握手／工具发现及 Skill 枚举／加载。只使用控制协议或官方 provider，不发送模型消息，不打开 STAR，不更新日常安装，不发布 npm／PyPI 包。

DSH 索引只收录具有真实发布来源的版本；未提交源码通过本地 bundle 验证，不伪造发布 commit 或时间。远端安装采用 GitHub Raw 索引和固定 commit 的 Git 来源。

复用两个仓库适用的现有检查，不新增自动测试文件，不增加模型工作流或真实算例验收。静态索引验证、本地安装验证和已发布市场安装分别记录。任务状态见 [TODO](../../TODO.md#市场接入与安装验证)，实际结果与限制见[分发说明](../distribution.md#本地安装验证2026-11-03)。
